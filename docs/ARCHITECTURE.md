# Architecture

## Client

`web/app.js` renders the interface and coordinates local storage, rules, gestures, the coin wallet and online polling. `table.js` renders each game's table; `table-responsive.css` owns adaptive layouts. Card faces are SVG generated by `court.js` / `court-detailed.js`; fonts are bundled locally. `table-motion.js` compares committed snapshots so sorting and selection do not replay draws or discards.

The rules modules (`marriage.js`, `games.js`, `dahar.js`, `faras.js` and supporting modules) also run on the server. Scorekeeping and playable rounds are separate: manual physical-table records may include events that a digital dealer prevents. `marriage-breakdown.js` explains each round's transfers.

`wallet.js` and `game-economy.js` implement virtual coins, budgets, pots and settlement. The offline wallet is local entertainment state, not a secure monetary balance. Online friend-table balances are separate.

## Multiplayer and live scores

`server/rooms.mjs` validates room membership, revisions and moves; `server/multiplayer.mjs` orchestrates all seven games. Private hands are filtered for each viewer. The room creator controls dealing/settings. Seat credentials are randomly generated bearer tokens; the six-digit room code is an invitation, not an account password.

`server/scores.mjs` handles shared score records, read-only guests and ownership transfer. A shared score link permits joining the record; share it only with intended viewers.

The local server keeps stores in memory. Cloudflare's `RoomCoordinator` persists room/score snapshots and expiry alarms in a Durable Object. API requests pass through `deploy/cloudflare/worker.mjs`, which serves the `/dashaincards` prefix and enforces configured origins.

## Offline and Android

The service worker caches a versioned set of application assets. Add new runtime modules to its asset list and bump its cache version when changing deployed assets.

Android bundles a generated copy of `web/` and serves it at the app-assets origin. `MainActivity.java` handles navigation, import/export and display rotation. `scripts/build.mjs` regenerates those assets; never edit the copied Android files directly.

## Data and boundaries

Local games, player names and records remain in the browser/WebView's storage. Online names, moves, hands and shared records reach the configured service. The deployed frontend is public configuration; no API credential belongs in `web/`. JSON backups contain names and scores. Keep them outside Git and share intentionally.

The production deployment configuration, provider sessions, signing keys and generated APKs are not source. They remain ignored locally.

## Preferences and audio

`play-preferences.js` resolves complete quick-play defaults without mutating stored or active rules. Game-default forms persist to the existing per-game options, and apply only when starting a new deal. Settings is available in the home navigation and as an in-table modal.

`audio.js` synthesizes an original offline loop and effects with Web Audio. Audio creation/resume is gesture-gated; background visibility and Android lifecycle events stop voices and scheduling. Audio preferences use the separate `dashain-audio-v1` local-storage key. Committed snapshot comparisons avoid replaying move/result sounds on sorting, polling or reload. No external audio files or third-party music service is used.
